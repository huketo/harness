# 한국어 스타일 레퍼런스

한국어로 SNS·블로그 글이나 기술 문서를 쓰거나 고칠 때 읽는다. [공통](#공통) 절은 항상 적용하고, 그다음 맥락에 맞는 절 하나([SNS·블로그](#sns블로그), [기술 문서](#기술-문서))를 적용한다. 화면 문구는 `awesome-interface`의 `references/writing.md`가 맡는다. 프로젝트의 용어집과 문체 지침, 필자가 준 문체 견본은 이 문서보다 우선한다.

AI 문체 패턴은 고칠 후보이고, 사람이 쓴 글인지 판정하는 기준이 아니다. **강함** 패턴은 한 번만 보여도 고친다. **약함** 패턴은 같은 문단에 다른 패턴이 함께 있을 때만 고친다. 인용문, 고유명사, 작품 제목, 그 표현 자체를 다루는 문장은 고치지 않는다.

## 공통

### 사실과 의미

- 원문과 사용자가 준 사실만 쓴다. 이름, 수치, 날짜, 인용, 원인, 순위를 새로 만들지 않는다. 필요한 사실이 없으면 문장을 단순하게 쓰고 확인할 항목으로 남긴다.
- 고치기 전에 보호 항목을 정하고 글자 그대로 둔다: 수치와 단위, 인용문, 코드·명령·경로·URL, 제품명과 식별자.
- 고친 뒤 원문과 문장 단위로 대조한다. 시제와 상태(예정과 완료), 양태(`~할 수 있다`와 `~한다`), 부정(`~하지 않았다`와 `~하지 못했다`), 범위를 정하는 작은 말(만, 도, 약, 최대, 최소, 이상, 이하, 아직, 일부, 모든)이 원문과 같아야 한다.
- 관찰을 권고로, 예측을 약속으로, 지침을 의무로 바꾸지 않는다.

### 어조와 종결어미

한 글 안에서는 높임 등급 하나를 유지한다. 기존 글이 있으면 그 등급을 따르고, 없으면 아래 기본값을 쓴다.

| 맥락 | 기본 종결어미 |
| --- | --- |
| SNS | 계정이 평소 쓰는 말투. 없으면 X는 해요체, LinkedIn과 공식 발표는 합니다체 |
| 블로그 | 합니다체 또는 해요체 중 하나 |
| 기술 문서 | 공유·외부 문서는 합니다체, 내부 설계 메모는 -다체 |

- 사물에는 높임을 붙이지 않는다: "자료가 준비되셨습니다"가 아니라 "자료가 준비됐습니다".
- 독자를 "당신"이나 "사용자님"으로 부르지 않는다. 주어를 생략하거나 할 일을 주어로 쓴다.

### 문장

- 의미가 있는 문장 성분을 생략하지 않는다. "그러면 경고가 붙는다"가 아니라 "그러면 작업 중인 파일에도 경고 표지가 추가된다".
- 조사와 어미를 생략하지 않는다. 명사 나열("컨텍스트 압축 전 신중 반영")이 아니라 조사·어미가 붙은 문장("컨텍스트가 압축되기 전에 신중하게 반영한다")으로 쓴다. 제목과 목록 항목은 예외다.
- 서술어와 종결어미로 문장을 끝맺는다.
- 한 문장에 내용 하나를 담는다. 행위자가 둘 이상이면 문장을 나누고, 수식어는 꾸미는 말 바로 앞에 둔다. 문단은 4문장 안팎에서 나눈다.
- 일반 어휘 자리에 비유 어휘를 쓰지 않는다. "분석의 흐름"이 아니라 "분석의 방향", "코드로 박는다"가 아니라 "코드에 명시한다". 해당 분야에서 정착한 관용 표현은 그대로 둔다.
- 사물을 사람처럼 쓰지 않는다. "이 기술은 빠른 처리를 가능하게 한다"가 아니라 "이 기술로 빠르게 처리할 수 있다", "서비스가 든든하게 버텼다"가 아니라 "장애 중에도 응답 오류율이 0.1% 아래였다"(수치가 있을 때).
- 사전에는 있지만 통용되지 않는 어휘 대신 실제로 쓰이는 어휘를 고른다.
- 엠대시(—)는 쉼표, 괄호, 콜론, 접속어로 바꾼다.

- 사물을 사람처럼 쓰지 않는다. "이 기술은 빠른 처리를 가능하게 한다"가 아니라 "이 기술로 빠르게 처리할 수 있다", "서비스가 든든하게 버텨 주었다"가 아니라 "장애 중에도 서비스가 응답했다".

- 빈 틀을 지운다: `~에 대한`, `~를 통해`, `~와 관련하여`, `~에 있어(서)`, `~라는 점에서 의미가 있다`.
- 우리말 동사로 바꾼다: 의미를 가지다 → 의미가 있다, 존재하다 → 있다, 회의를 갖다 → 회의를 열다, 필요로 하다 → 필요하다, ~에 위치한 → ~에 있는.
- 명사화를 동사로 푼다: 검토를 진행하다 → 검토하다, 절감이 가능하다 → 줄일 수 있다.
- 이중 피동과 불필요한 사동을 고친다: 되어지다 → 되다, 보여지다 → 보이다, 개선시키다 → 개선하다.
- 겹친 말을 줄인다: 매년마다 → 매년, 새로운 신제품 → 신제품, 약 30여 명 → 30여 명. `의`가 이어지면 하나만 남긴다.
- 반복되는 `또한`, `그리고`, `한편`과 `~하며 ~하면서 ~함으로써`로 이어지는 문장을 끊는다. 인과·조건·양보를 나타내는 접속어는 남긴다.
- 목록 항목은 같은 문법 형태로 맞춘다.

### AI 문체 패턴

| 패턴 | 예 | 고치는 방향 | 강도 |
| --- | --- | --- | --- |
| 대비 연출 | "단순한 X가 아니라 Y", "단순히 ~를 넘어", "~에 그치지 않고" | Y를 바로 말한다. 독자가 실제로 X라고 믿을 때만 대비를 남긴다 | 강함 |
| 마무리 한 줄 | "이것은 단순한 숫자가 아닙니다.", "결국 중요한 것은 사람입니다", "~라고 해도 과언이 아니다" | 지우거나 앞 문장의 구체적 결과로 바꾼다 | 강함 |
| 격언·본질 | "핵심은 ~입니다", "진짜 문제는 ~" | 감춘 주장을 그대로 쓴다 | 강함 |
| 무대 연출 서두 | "오늘은 ~에 대해 알아보겠습니다", "자, 그럼 시작해 볼까요?" | 첫 문장에서 내용을 말한다 | 강함 |
| 상대 없는 반박 | 아무도 말하지 않은 "~라고 생각할 수 있지만" | 지운다. 실제 반론은 출처와 함께 다룬다 | 강함 |
| 대화 흔적 | "좋은 질문입니다", "도움이 되셨기를 바랍니다", "궁금한 점이 있으시면 언제든지" | 지운다 | 강함 |
| 시대 배경 서두 | "오늘날 빠르게 변화하는 디지털 환경에서" | 지운다 | 강함 |
| 의미 부풀리기 | "패러다임 전환", "새로운 장을 열었다", "귀추가 주목된다", "밝은 미래" | 사실만 남긴다 | 보통 |
| 상투 형용사 | 혁신적인, 획기적인, 놀라운, 강력한, 효과적으로, 성공적으로 | 수치나 구체 사실로 바꾸고, 없으면 지운다 | 보통 |
| 내용 없는 "다양한" | "다양한 기능을 제공합니다" | 종류를 적거나 지운다. "여러"로 바꾸는 것은 고친 것이 아니다 | 보통 |
| 출처 없는 권위 | "전문가들은 ~라고 봅니다" | 출처를 밝히거나 지운다 | 보통 |
| 추측으로 채우기 | 근거 없는 "~인 것으로 보입니다" | "확인되지 않았다"로 쓰거나 지운다 | 보통 |
| 장식 서식 | 이모지 머리 목록, 제목 이모지, 의미 없는 굵게, 설명을 반복하는 "**라벨**: 설명" | 문장이나 평범한 목록으로 바꾼다 | 보통 |
| 능력 표현 반복 | 한 단락에 "~할 수 있습니다" 3회 이상 | 실제 능력만 남긴다 | 약함 |
| 셋으로 맞춘 나열 | 내용이 둘인데 항목 셋 | 의미만큼 항목을 둔다 | 약함 |
| 글에 대한 글 | "이 글에서는 ~을 소개합니다", "아래 표는 ~를 비교합니다" | 주제를 바로 쓴다 | 약함 |
| 첫째·둘째·셋째 반복 | 구조가 이미 보이는 목록의 순서어 | 지운다 | 약함 |

이메일·공지의 인사와 맺음말은 관례이고 패턴이 아니다. "오늘은"은 실제 날짜나 대조를 나타내면 남기고, "최선을 다하겠습니다"는 고칠 때 구체적인 조치로 바꾼다.

### 표기

- 조사는 붙이고 의존명사는 띄운다. 숫자 뒤 단위는 붙여도 띄워도 되므로(`10명`, `10 명`) 한 글 안에서 하나로 통일한다.
- 문장은 마침표로 끝낸다. 제목과 표어에는 마침표를 찍지 않는다. 명사형으로 끝나는 목록 항목은 한 목록 안에서 마침표 사용을 통일한다.
- 금액과 큰 수는 천 단위 쉼표를 쓴다(`3,000원`). 범위는 원문 표기(`3~5일`)를 유지한다.
- 직접 인용은 큰따옴표, 강조는 작은따옴표를 쓴다. 원문의 따옴표 종류는 바꾸지 않는다.
- 외래어는 국립국어원 표기를 따른다(콘셉트, 메시지). 코드, 제품명, API 필드, 명령은 번역하지 않는다.

## SNS·블로그

- 필자의 문체 견본이 있으면 견본의 문장 길이, 어휘, 문장부호를 따른다. 견본이 없으면 필자의 의견, 불확실함, 구체적인 경험을 남기고, 깔끔한 교훈을 새로 덧붙이지 않는다.
- 첫 문장에 무엇이 바뀌었는지나 어떤 상황인지 쓴다. "드디어!", "여러분, 이거 아셨나요?" 같은 서두로 시작하지 않는다.
- 출시·공지 글은 지원 범위, 제한, 정해지지 않은 일정을 숨기지 않는다. 미정인 일정은 미정이라고 쓴다.
- 자료의 항목을 한 문장에 하나씩 옮겨 적지 않는다. 독자에게 중요한 순서로 사실을 묶고, 이어지는 사실은 연결어미로 잇는다: "결제 화면을 새로 만들었고, 카드 등록 단계를 하나 줄였습니다".
- 자료에 적힌 작성 지시(예: "가격은 아직 공개하지 않는다")는 따르기만 하고 게시글에 문장으로 옮기지 않는다.
- 자료의 표현과 어순을 그대로 옮기지 않고 한국어로 보통 말하는 형태로 쓴다. 자료가 다른 언어일 때도 같다: "회사 20곳이 참여"보다 "20개 회사가 참여".
- SNS 게시물 하나에는 요지 하나를 담는다. 해시태그는 실제로 검색되는 것만 0~3개 쓴다. 이모지는 계정 관례가 있을 때만 쓰고 단어 대신 쓰지 않는다. "좋아요·공유 부탁드려요" 대신 링크나 정보로 마무리한다.
- 글자 수 제한은 게시 전에 현재 값을 확인한다. X는 한글 한 글자를 영문 두 글자로 세므로, 일반 계정에서 한국어 게시물은 140자 안팎이 한도다.
- 블로그 글의 구조는 `writing-for-humans`의 `post` 장르를 따른다.

## 기술 문서

- 결론을 먼저 쓴다. 절차는 번호 목록으로 쓰고, 조건은 지시 앞에 둔다.
- 용어는 첫 등장에 정의한다. "한국어 용어(English term)" 병기는 독자에게 도움이 될 때 첫 등장에 한 번만 쓴다. 같은 개념에 다른 표기를 섞지 않는다.
- 코드, 명령, 경로, 설정 키는 백틱으로 감싸고 번역하지 않는다.
- 상태를 정확히 쓴다. 프로토타입, 검증, 스테이징을 운영으로 쓰지 않는다. 내부 추정을 확정치로 쓰지 않는다.
- 목록의 "라벨: 설명" 형식은 값이나 이름에 설명이 붙는 항목에만 쓴다. 라벨이 설명을 되풀이하면 한 문장으로 합친다.
- 비교는 표, 순서는 번호 목록, 병렬 항목은 글머리 목록으로 쓴다. 한 문단으로 전달되는 내용을 목록으로 쪼개지 않는다.

## 검수

1. 원문 대비 추가되거나 빠진 사실이 0건이다. 수치, 이름, 날짜, 부정, 범위를 정하는 작은 말을 대조했다.
2. 종결어미 등급이 하나다.
3. 강함 패턴이 0건이고, 약함 패턴이 겹친 문단이 0곳이다.
4. 번역투, 이중 피동, 명사 덩어리, 비유 어휘를 점검했다.
5. 엠대시, 이모지 머리 목록, 의미 없는 굵게가 0건이다.
6. 단위 띄어쓰기, 천 단위 쉼표, 따옴표가 한 글 안에서 통일되어 있다.
7. 적용한 맥락 절의 항목을 모두 확인했다.
