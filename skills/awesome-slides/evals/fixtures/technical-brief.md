# 기술 발표 입력: 평균보다 꼬리 지연을 먼저 확인하기

이 자료와 CSV는 공개 가능한 교육용 합성 사례이다. 실제 회사, 제품, 운영 환경 또는 실험 결과가 아니다. 슬라이드에서 이 경계를 짧게 표시하고, 합성 결과를 현업 성능 향상으로 주장하지 않는다.

## 청중과 목적

- 청중: TypeScript를 읽을 수 있는 백엔드 엔지니어.
- 15분 발표이며 마지막 2분은 질문/정리용이다.
- 목표: 평균만 보고 정상이라고 판단하지 않고, p95와 대기/처리 시간 분해를 함께 확인하는 진단 순서를 익힌다.
- 언어: 한국어. 코드와 식별자는 원문을 유지한다.
- 디자인: 밝은 종이색 배경, 짙은 남색 글자, 청록 강조. 절제된 기술 발표이며 과도한 장식은 필요 없다. 스타일 추가 승인 없이 제작한다.
- 산출물: Slidev 편집 원본, 실행 가능한 웹 빌드, PDF, 발표자 노트. 9~12장을 출발점으로 하되 설명에 맞게 조정한다.

## 근거 데이터

`requests.csv`는 두 합성 구간 각각 20개 요청이다. 시간 단위는 ms이다. 각 요청의 총시간은 queue_ms + service_ms이다. 측정 도구를 실제 실행했다고 주장하지 않는다. 평균과 nearest-rank p95를 CSV에서 계산한다. nearest-rank p95는 정렬한 N개 값의 ceil(0.95*N)번째 값이다.

A: 20개 요청 모두 queue=20, service=80.
B: 18개 요청은 queue=0, service=60; 2개 요청은 queue=380, service=80.
두 구간의 평균 총시간은 같지만 p95와 대기 시간 분포는 다르다. 이 작은 데이터로 실제 서비스 SLO나 통계적 유의성을 결론내릴 수 없다.

## 코드와 설명할 관계

`latency.mjs`는 이 fixture의 순수 계산 함수이다. 코드 전체를 한 장에 붙이지 말고, 총시간과 p95를 읽는 데 필요한 부분만 보여준다. 전체 코드는 입력 자료에 남아 있다. `requestQueueResidenceTimeMilliseconds`처럼 긴 식별자도 코드/도식에서 잘리지 않아야 한다.

서사의 필수 내용:
1. 평균이 같아도 일부 요청은 훨씬 늦을 수 있다는 관찰.
2. 대기 → 처리 → 응답의 시간 분해.
3. 평균과 p95의 의미, 여기서 사용한 p95 계산법.
4. A/B 데이터를 같은 축과 단위로 비교.
5. 평균 지표 → p95 → 대기/처리 분해 → 원인 가설 확인 순서.
6. 표본 수와 합성 자료의 한계.
7. 다음 행동: 현재 서비스의 총시간과 대기 시간 계측 위치를 확인한다.

최소 하나의 과정/구조 도식과 하나의 데이터 비교 시각화를 포함한다. 각 본문 장의 노트에는 설명·전환·예상 시간을 적고, 실제로 발표해 시간을 측정했다고 쓰지 않는다.
