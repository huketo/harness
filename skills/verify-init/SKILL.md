# Verify init

저장소마다 실제 앱을 띄우고, 사용자가 하듯 기능을 조작하고, 증거를 남기는 정해진 방법이 있어야 한다. 이 스킬은 그 방법을 저장소 전용 스킬로 만든다. 만든 스킬을 읽는 쪽은 사람이 아니라, 작업 도중에 이 앱을 처음 보는 다음 에이전트다.

만드는 위치는 `.agents/skills/verify-<앱>/`이다. Claude Code는 `.claude/skills/`를 읽으므로 `.claude/skills/verify-<앱>`을 `../../.agents/skills/verify-<앱>`으로 가는 상대 심링크로 둔다. `full-send`는 이 두 위치 가운데 한 곳에 `verify-*/SKILL.md`가 있어야 머지한다.

## 1. 저장소를 조사한다

코드에서 답을 찾고, 관측할 수 없는 것만 사람에게 묻는다.

- **표면:** 사용자가 실제로 만지는 것(웹 UI, CLI·TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리). 여러 개면 주된 것 하나를 고르고 나머지를 적는다.
- **실행:** 로컬에서 앱을 띄우는 방법. 저장소가 문서로 정한 명령을 우선한다. 포트, 환경 변수, 시드 데이터, 인증을 적는다.
- **조작:** 에이전트가 앱을 조작할 수단. 저장소에 이미 있는 장치(Playwright 스펙, PTY 헬퍼, curl로 부를 수 있는 엔드포인트)를 먼저 쓴다. 없으면 표면에 맞는 수단을 고른다: 웹은 브라우저 자동화, 데스크톱은 `computer-use`, 모바일은 하네스의 기기 도구, CLI·TUI는 PTY나 tmux, 서비스는 HTTP.
- **관측:** 남길 수 있는 증거(스크린숏, 터미널 기록, 응답 본문, 로그, 종료 코드, 저장된 값).
- **격리:** 인스턴스 둘을 나란히 띄울 수 있는지(포트, 데이터 디렉터리, 프로필). 띄울 수 없으면 만든 스킬에 그 사실을 적는다. 사람이 쓰는 인스턴스를 함께 조작하는 것보다 거절하는 편이 낫다.

체크아웃이 그대로는 빌드되거나 실행되지 않으면 먼저 고치거나 정확히 보고한다. 깨진 상태를 기준으로 쓴 스킬은 틀린 절차를 가르친다.

## 2. 스킬을 만든다

`SKILL.md`에는 프런트매터(`name: verify-<앱>`, 앱과 표면과 쓸 때를 말하는 `description`)와 아래 절을 둔다. 모든 절은 조사에서 실제로 찾은 명령·경로·이름으로 채우고 자리 표시를 남기지 않는다.

- **Launch:** 검증용으로 앱을 띄우는 정확한 명령과, 쓸 수 있는 상태가 됐음을 아는 방법. 빈 데이터 디렉터리에서 시작해 마이그레이션과 시드까지 끝나야 한다. 프로세스가 응답하는 것만으로는 준비된 것이 아니다. 종료 방법도 적는다. 금방 끝나는 CLI는 한 번 빌드하고 조작마다 격리된 세션을 새로 연다.
- **Doctor:** "이 인스턴스를 조작해도 되는가"에 답하는 읽기 전용 검사 하나(프로세스, 빌드 버전, 포트의 주인, 인증). 무언가 이상하면 이것부터 실행한다.
- **Drive:** 이 저장소의 실제 선택자와 명령으로 쓴 조작 방법. 좌표나 탭 순서보다 안정적인 손잡이(ARIA 이름, data 속성, 프롬프트 문자열, 라우트 경로)를 쓴다.
- **Evidence:** 무엇을 어디에 남기는지와 증거의 기준.
  - 내부 setter나 테스트 전용 엔드포인트가 아니라 사용자의 실제 경로를 조작한다.
  - 마지막 화면만이 아니라 조작과 그 결과 상태를 함께 남긴다.
  - 보이는 것과 함께 부수효과(쓴 파일, 넣은 행, 보낸 메시지)를 확인한다.
  - 모의 객체는 운영에서도 이미 외부 시스템을 분리하는 경계에서만 쓴다.
  - dry-run이나 테스트 모드는 이름을 믿지 않고 실제로 무엇을 건너뛰는지 관측한다.
  - 증거는 버전 관리 밖의 정해진 경로에 둔다.
- **Cleanup:** 이번 실행이 만든 인스턴스를 내리는 방법. 프로세스 이름으로 죽이지 않고 자기가 띄운 것만 죽인다. 정리는 인스턴스와 임시 상태만 지우고 증거는 남긴다.
- **Helpers:** 스킬에 딸린 스크립트는 실행 가능하고, 호출 방법이 본문에 적혀 있다.

## 3. 기능 지도를 만든다

`features/README.md`와 사용자 기능마다 파일 하나를 만든다. 라우트, 명령, 메뉴, 문서에서 찾은 상위 3~5개로 시작한다. 모양은 [references/feature-map-example/](references/feature-map-example/README.md)을 따른다. 기능 파일은 사용자 관점의 한 문단으로 시작하고, H2 네 개를 이 순서로 둔다: `Sub-features`, `How to get to it (user POV)`, `Driving it with <수단>`, `Gotchas`.

지도는 "왼쪽 사이드바의 그것"이 무엇인지 사람과 에이전트가 같은 이름으로 부르게 하는 공유 어휘다. 구현 세부는 넣지 않는다. 시드 데이터에 전제 조건이 빠져 조작이 실패하면 실패를 보고하고 이유를 그 기능의 `Gotchas`에 적는다. 통과시키려고 조작을 약하게 만들지 않는다.

## 4. 넘기기 전에 증명한다

만든 스킬의 지시를 처음부터 끝까지 한 번 따른다: launch, doctor, 지도의 기능 하나를 drive, 증거 수집, cleanup. 정리한 뒤 증거가 정한 경로에 남아 있는지 확인한다. 실패한 시도 뒤에도 cleanup을 실행해 프로세스와 포트를 남기지 않는다. 한 번도 실행하지 않은 스킬은 초안이다.

실제 대상 대신 다른 환경(원격 대신 로컬 스택)에서 증명했으면, 그 환경이 대신 해 준 준비 단계를 모두 적는다. 그 단계들은 실제 대상에서 실행되기 전까지 미확인이다.

완료 기준: 기능 하나의 증거 파일이 정리 뒤에도 남아 있고, 이번 실행이 띄운 프로세스가 없다.

## 5. 지도를 맞춘다

앱의 기능, 진입 경로, 선택자, 실행 명령을 바꾸는 변경은 같은 변경에서 지도의 해당 파일을 고친다. 지도가 앱과 어긋났다고 의심되면 소스로 바뀐 곳을 찾고, 어긋난 기능을 한 번씩 실제로 조작해 확인한 것만 고친다. 확인하지 못한 수정은 지도에 넣지 않는다.

## 보고

만든 파일, 고른 표면과 조작 수단, 지도에 넣은 기능, 증명에 쓴 기능과 증거의 경로, 미확인으로 남은 단계, 나란히 띄울 수 없으면 그 사실을 적는다.
