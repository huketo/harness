# Make skill

스킬은 에이전트가 따르는 작업 절차서다. 쓸 만한 절차서는 세 가지를 갖춘다. 실제로 일어난 실패를 막고, 그 직무가 이미 검증한 방법에 기대며, 없을 때보다 나아졌다는 것이 실행으로 확인되어 있다. 이 스킬은 그 셋을 순서대로 확보한다. 문장을 쓰는 기준은 `writing-for-agents`가 소유한다.

변경의 크기에 맞는 길로 들어간다.

| 변경 | 길 |
| --- | --- |
| 오타, 깨진 링크, 뜻이 같은 표현 | 고치고 끝낸다. 아래 절차를 밟지 않는다. |
| `description`만 | 5절의 선택 시험만 한다. |
| 본문, 절차, 스크립트, 새 스킬 | 1절부터 한다. |

## 1. 근거를 모은다

만들 이유는 둘 중 하나다.

- **실패:** 에이전트가 같은 일을 두 번 잘못했다. 세션 기록, 리뷰 댓글, 사람의 교정, 이슈에서 사례를 찾는다.
- **새 능력:** 에이전트가 지금은 못 하는 일이다. 사람이 실제로 입력할 요청문 두 개를 적는다. 못 한다는 것은 3절의 실행이 보여 준다.

요청은 받았는데 실패 사례를 찾지 못했으면 스킬을 쓰지 않는다. 어디를 찾아봤는지와, 어떤 사례가 있으면 만들 수 있는지를 보고하고 끝낸다.

완료 기준: 실패 사례 두 개의 근거(`path:line`, 커밋, 댓글 링크)나 요청문 두 개가 있다.

## 2. 해법을 찾는다

위에서부터 내려오며 처음으로 통하는 단을 고른다. 아래 단일수록 에이전트가 건너뛰기 쉽다.

1. **검사로 막는다.** 구조, 타입, 린트, 테스트가 그 실수를 거부할 수 있으면 `correct`로 넘기고 스킬을 쓰지 않는다.
2. **도구에 맡긴다.** 그 일을 이미 하는 명령, 라이브러리, 서비스를 찾는다. 있으면 스킬은 그 도구를 이 저장소에서 언제 어떻게 쓰는지만 담고, 도구가 하는 일을 다시 설명하지 않는다.
3. **알려진 방법론을 가져온다.** 그 직무가 써 온 방법을 `research`로 1차 자료에서 확인한다. 모델은 이름난 방법을 이미 알고 있으므로, 이름을 부르고 달라지는 부분만 적는다.
4. **다른 팀의 사례를 가져온다.** 공개된 엔지니어링 글과 스킬에서 같은 문제를 푼 절차를 찾는다. 글을 옮겨 오면 라이선스와 출처 기록을 남긴다.
5. **직접 만든다.** 위의 넷이 모두 없을 때만 한다.

가져온 방법은 에이전트에 맞춘다. 단계마다 그 단계가 막는 실패를 적고, 아래 표로 거른다.

| 사람의 제약에서 온 단계 | 에이전트에게는 |
| --- | --- |
| 회의 일정, 역할 분담, 피로를 줄이려는 단계 | 뺀다. |
| 기억에 의존하는 단계 | 상태를 파일에 적게 한다. 세션이 바뀌면 기억이 없다. |
| "확인했다"는 말로 넘어가는 단계 | 실행한 명령과 출력을 남기게 한다. |
| 한 사람이 차례로 하는 검토 | 다른 계열 모델의 독립 검토로 바꾼다. 병렬 실행이 싸다. |
| 끝을 사람의 감으로 정하는 단계 | 확인할 수 있는 완료 기준을 붙인다. 에이전트는 일찍 끝내려 한다. |

완료 기준: 스킬 디렉터리의 `METHOD.md`에 고른 단, 출처(URL이나 서지), 가져온 것, 에이전트에 맞춰 바꾼 것과 이유, 더 높은 단이 통하지 않은 이유가 있다. `METHOD.md`는 `SKILL.md`에서 가리키지 않는다. 스킬을 고치는 쪽만 읽는다.

## 3. 사례를 쓰고 스킬 없이 실행한다

사례는 `evals/evals.json`에 쓴다. 형식은 [`lib/evals.ts`](../../scripts/skill-eval/lib/evals.ts)가 소유한다.

- 근거마다 사례 하나를 쓰고, 스킬이 필요 없는 일상 요청 하나를 더한다. 일상 사례는 스킬이 작은 일에 과정을 더하지 않는지를 본다.
- `prompt`는 사람이 입력할 문장 그대로 쓴다. 기대하는 답과 스킬 이름을 넣지 않는다.
- 프롬프트, fixture의 파일과 디렉터리 이름에 eval, test, 평가, 채점처럼 시험임을 알리는 단어를 넣지 않는다. 시험인 줄 아는 에이전트는 다르게 행동한다.
- fixture는 실패를 재현하는 가장 작은 합성 파일이다. 근거가 된 기록과 같은 모양으로 새로 쓰고, 실제 이름, 수치, 본문은 옮기지 않는다. 실행되는 프로젝트를 새로 짓지 않는다.
- `expectations`는 남은 파일과 마지막 답으로 판정할 수 있게 쓴다. "무엇을 적용했다고 말한다"가 아니라 "어떤 파일이 생겼다", "답에 어떤 출력이 실려 있다"로 쓴다. 채점자는 실행 기록을 받지 않으므로, 어떤 명령을 실행했는지는 `transcript.jsonl`에서 직접 확인한다.

사례 대신 테스트가 근거가 되는 경우가 둘 있다. 어느 쪽이든 `METHOD.md`에 이유를 적는다. 4절과 5절의 완료 기준, 6절의 전후 표는 실행한 사례에만 적용한다. 사례가 하나도 없으면 6절의 표와 발췌 자리에 테스트의 실패 출력과 통과 출력을 넣고, 사례로 실행하지 못한 `SKILL.md`의 줄을 "미실행"으로 적는다.

- **해법이 스크립트다.** 2절에서 실패를 스킬의 스크립트나 검사로 막기로 했으면, 수정 전에 실패하고 수정 뒤에 통과하는 테스트가 그 실패의 근거다. 아래 실행과 5절의 비교는 `SKILL.md`에 새로 남는 줄에만 한다.
- **실행기가 상태를 준비하지 못한다.** 실행기는 파일만 복사한다. 원격 저장소, MR·PR, CI, 로그인처럼 파일로 둘 수 없는 상태에서만 일어나는 단계에는 사례를 쓰지 않는다. 그 상태를 흉내 내는 프로젝트를 fixture로 짓지 않는다.

그 밖에는 스킬을 쓰기 전에 스킬 없이 실행한다.

```bash
node scripts/skill-eval/from-evals.ts --skill skills/<name>
node scripts/skill-eval/run.ts --suite var/skill-eval/suites/<name>/suite.json --model <스킬을 쓸 모델> --effort high --arm none
```

출력(`final.md`, `diff.patch`, `transcript.jsonl`)을 직접 읽고 사례마다 어느 기대가 실패했는지 적는다. 모든 사례가 통과하면 사례가 실패를 재현하는지 한 번 고쳐 보고, 그래도 통과하면 스킬을 쓰지 않는다. 모델이 이미 하는 일을 적은 스킬은 비용만 든다.

실행은 사례 다섯 개까지, 갈래마다 한 번씩은 묻지 않고 한다. 그보다 많이 돌려야 하면 예상 비용을 말하고 묻는다. 실행기는 이 스킬이 들어 있는 저장소의 스킬만 실행한다. 다른 저장소에서는 사례마다 같은 요청을 새 세션 둘(스킬 없음, 스킬 있음)에 보내고 출력을 직접 읽어서 비교한다. 실행기나 채점기를 새로 만들지 않는다.

완료 기준: 사례마다 스킬 없는 실행의 출력과, 실패한 기대의 목록이 있다.

## 4. 가장 작게 쓴다

`writing-for-agents`를 불러 그 기준으로 쓴다. 실패의 종류가 글의 형태를 정한다.

| 실패 | 형태 |
| --- | --- |
| 순서를 건너뛰거나 일찍 끝낸다 | 단계와, 단계마다 확인할 수 있는 완료 기준 |
| 결과물의 모양이 틀린다 | 틀이나 예시 하나 |
| 항목을 빠뜨린다 | 틀 안의 필수 칸 |
| 계산, 변환, 검사를 틀린다 | 스크립트. 글로 설명하지 않는다. |
| 알면서 다른 길을 택한다 | 해야 할 행동을 먼저 쓰고, 금지는 그 뒤에 한 줄 |

3절에서 실패한 기대를 통과시키는 데 필요한 줄만 쓴다. `description`에는 언제 쓰는지만 적고 절차를 요약하지 않는다. 요약이 있으면 에이전트는 본문을 읽지 않고 요약을 따른다.

완료 기준: 본문의 모든 절이 3절에서 실패한 기대 하나 이상과 이어진다.

## 5. 비교한다

스킬을 커밋하고 같은 사례를 다시 실행한 뒤 채점한다. 기존 스킬을 고쳤으면 `--previous <고치기 전 커밋>`을 더해서 고치기 전과도 비교한다.

```bash
node scripts/skill-eval/from-evals.ts --skill skills/<name> [--previous <gitref>]
node scripts/skill-eval/run.ts --suite var/skill-eval/suites/<name>/suite.json --model <같은 모델> --effort high
node scripts/skill-eval/grade.ts --iteration-dir <실행이 출력한 디렉터리>
```

채점은 다른 계열 모델이 어느 쪽이 스킬인지 모르는 채로 한다. `benchmark.md`를 읽고, 판정이 자신이 읽은 것과 다르면 그 기대가 모호한 것이므로 기대를 고친다.

- 실패했던 기대가 여전히 실패하면, 그 실패를 설명하는 가장 작은 지시를 고치고 그 사례만 다시 실행한다. 실행하지 않은 수정은 "미실행"으로 적는다.
- 일상 사례에서 턴 수나 시간이 늘었으면 진입 조건을 좁힌다.

이웃 스킬과 설명이 겹치면 선택 시험을 한다. [`scripts/skill-eval/routing/`](../../scripts/skill-eval/routing/)의 사례 파일에 이 스킬로 와야 할 요청과, 이웃 스킬로 가야 할 요청을 적는다. 설명은 커밋에서 읽으므로, 고친 설명을 커밋한 뒤 `node scripts/skill-eval/route.ts --cases <파일>`을 실행한다.

완료 기준: 3절에서 실패한 기대가 모두 통과하고, 일상 사례가 스킬 없는 실행보다 나빠지지 않았다. 통과하지 못한 기대는 이유와 함께 남긴다.

## 6. 보고한다

MR·PR 본문에 아래를 붙인다.

- 사례별 전후 표(`benchmark.md`에서 옮긴다)와 실행한 모델.
- 스킬 없이 실패한 출력과 스킬로 고쳐진 출력의 발췌 하나.
- `SKILL.md`의 줄 수 변화(`이전 → 이후`).
- 고른 해법의 단과 출처 한 줄.
- 통과하지 못한 기대와 실행하지 않은 검사.
