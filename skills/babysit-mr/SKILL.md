# Babysit MR

리뷰 봇은 도움이 되지만 항상 옳지는 않다. 이 스킬은 MR 하나를 대기, 판정, 수정의 반복으로 준비 상태까지 끌고 간다. 머지는 사람이 요청했거나 `full-send`가 허용한 경우에만 한다.

## 대기

자체 감시 루프나 `sleep` 루프를 만들지 않는다. MR 하나에 감시자 하나만 쓴다. T3 안에서는 `watch_pull_request`, 그 밖에서는 `scripts/mr-wait`이다. 같은 MR에 둘을 함께 쓰지 않는다.

### T3: `watch_pull_request`

먼저 기존 파이프라인 결과와 댓글을 처리한다. 그다음 `watch_pull_request`를 호출하고 턴을 끝낸다. T3는 2분마다 확인하고, 검사 실패·통과, 다른 사람의 댓글·리뷰, 충돌이 생기면 이 스레드를 깨운다. GitLab MR도 같은 도구로 감시된다. 다만 GitLab에서는 다음이 다르다.

- 파이프라인은 `Pipeline`이라는 검사 하나로만 보이고, 잡별 실패와 필수 검사 구분이 없다. 실패한 잡은 `glab ci view`나 `glab api projects/<id>/pipelines/<pid>/jobs`로 직접 읽는다.
- 승인(approval)과 승인 철회는 깨우지 않는다. 시스템 note는 이벤트에서 빠지기 때문이다. 준비 상태 판단 전에 승인 상태를 직접 읽는다.
- 대상 브랜치가 앞서 나간 상태(rebase 필요)는 깨우지 않는다. 충돌만 깨운다.

규칙:

- MR을 소유한 스레드만 감시한다. `delegate_task` 자식(리뷰어, 카운슬 위원 등)은 감시하지 않는다.
- 깨움은 소식일 뿐 머지 결정이 아니다. 준비 상태는 직접 확인한다.
- 사람에게 넘길 때(준비 완료, 막힘, 질문) 먼저 `unwatch_pull_request`를 부른다. 감시 중인 스레드는 사람의 받은편지함에 나타나지 않는다. 머지나 닫힘은 감시를 저절로 끝낸다.
- "Stopped watching, could not read it"이 오면 GitHub에서는 `gh api rate_limit --jq .resources.graphql`, GitLab에서는 `glab auth status`와 `glab api user`로 원인을 확인한 뒤 한 번만 다시 감시한다. 짧은 간격으로 반복하지 않는다.

### 그 밖: `scripts/mr-wait`

이 스킬 디렉터리의 `scripts/mr-wait`를 절대 경로로 실행한다. GitHub PR과 GitLab MR을 모두 받는다.

```sh
mr-wait <번호|!iid|URL> [--repo group/sub/proj] [--host gitlab.example] [--until ready|green|any-change]
```

이벤트 한 건마다 한 줄을 출력한다. 조건을 만족하거나 머지되면 0, 사람의 조치가 필요하면(파이프라인 실패, 충돌, rebase 필요, 해결되지 않은 토론, 닫힘) 1, 입력 오류나 같은 MR의 두 번째 감시자면 2로 끝난다. GitLab의 `ready`는 head 파이프라인 성공, 막는 토론 해결, 남은 승인 0, 초안 아님, `detailed_merge_status == mergeable`이다. `green`은 head 파이프라인 성공만 본다.

Claude Code에서는 Monitor 도구(`timeout_ms: 3600000`)로 실행해 줄마다 깨어난다. Monitor가 없으면 한 번의 긴 명령으로 실행한다. 푸시한 뒤, 1로 끝난 원인을 처리한 뒤, 재개한 뒤에 다시 시작한다. 이미 보고한 이벤트를 기억하므로 사이에 생긴 일을 잃지 않는다. 다른 pid가 이미 감시 중이라고 하면 두 번째를 띄우지 않는다.

어느 감시자든 조치가 필요 없는 이벤트면 메시지 없이 턴을 끝낸다. "아직 기다리는 중" 같은 글을 쓰거나 올리지 않는다.

## 지적 처리

마지막 푸시 이후의 검사와 댓글만 다룬다. 봇의 지적은 모두 소스에서 확인한 뒤 고친다. 실제 지적과 파이프라인 실패는 고치고, 저장소 실패와 인프라 일시 장애를 구분한다. 근거 없는 지적은 이유를 적어 답하고 해결 처리한다. 사람을 대신하는 모든 댓글은 `leaving-mr-comments` 스킬을 따른다.

- **저장소의 리뷰 봇**: 저장소나 하네스에 그 봇의 결과를 소비하는 스킬이 있으면 지적, 완료 공지, 침묵, 재리뷰 판단을 그 스킬에 넘기고 이 스킬에서 같은 판단을 다시 하지 않는다. 그런 스킬이 없으면 다른 지적처럼 다룬다. 봇의 리뷰는 형식 승인(approval)이 아니므로 승인 조건과 따로 본다.
- `.macroscope/check-run-agents/*.md`가 있으면 Macroscope 지적에 답하기 전에 그 규칙을 읽는다.
- CodeRabbit은 참고용이다. 다른 지적처럼 다루되 기다리지 않고 머지를 막지 않는다.

MR은 사람의 목표가 필요로 하는 크기로 유지한다. 리뷰 반복은 값싸 보이는 수정을 하나씩 더해 MR을 키운다. 의도한 경우의 실제 버그만 고치고, 불필요한 테스트, 의미 없는 경우의 방어, 추가 연동·호환, 작은 성능 비용은 이유를 적어 거절하고 후속 작업으로 남긴다. 코드를 지우거나 좁히는 수정을 우선한다. 수정마다 증명(테스트, 재현)을 얻은 뒤 푸시한다.

## 대상 브랜치와 머지

대상 브랜치의 변화를 지켜보고 필요하면 rebase한다. `mr-wait`는 새 대상 커밋이 이 MR의 파일을 건드리면 알리고, rebase 필요·충돌을 알린다. `watch_pull_request`는 충돌만 알리므로 준비 상태라고 말하기 전에 뒤처짐을 직접 확인한다(GitLab `detailed_merge_status`, GitHub `mergeStateStatus`). 겹치는 다른 MR이 이 MR을 무의미하게 만들면 감시를 멈추고 사람에게 알리며, 닫는 것은 명시적으로 허용된 경우에만 한다.

바뀐 것이 없으면 조용히 있는다. `mr-wait`가 0으로 끝나거나 T3에서 머지 관문이 최신 head에서 통과하면 멈춘다. 머지는 사람이 명시적으로 요청했거나 `full-send`가 허용할 때만 한다. 그 밖에는 준비되었다고 보고한다. 머지 직전에는 `git fetch` 뒤 MR을 다시 확인한다. 뒤처졌거나 충돌하거나, 마지막 성공 파이프라인 뒤에 들어온 대상 커밋이 이 MR의 파일을 건드리면 머지하지 않고 rebase, 푸시, 재대기를 한다. GitLab 머지는 확인한 head에만 걸리도록 `glab mr merge <iid> --sha <head>`로 한다. 관리자 우회는 쓰지 않는다.
