# Harness flow

에이전트가 쓴 코드를 믿을 수 있게 만드는 스킬이 여럿이고, 대부분 사람이 이름으로 불러야 실행된다. 이 스킬은 그 목록을 대신 기억한다. 저장소의 현재 상태를 읽어 다음 단계 하나를 정하고, 상태로는 알 수 없는 사건별 스킬을 표로 보여 준다. 스스로 파일을 바꾸지 않는다.

## 1. 상태를 읽는다

저장소 루트에서 이 스킬 디렉터리의 `scripts/flow-status`를 절대 경로로 실행한다. 읽기만 하는 스크립트이며, 칸마다 무엇이 있는지와 마지막 줄에 `next`를 출력한다.

```sh
<이 스킬 디렉터리>/scripts/flow-status [저장소 경로]
```

결과를 칸별로 짧게 보여 준다. 스크립트는 파일과 항목이 있는지만 본다. 린트가 실제로 무엇을 막는지, CI가 무엇을 실행하는지는 판단하지 않으므로, 그렇게 말하지 않는다.

## 2. 다음 단계를 정한다

`next` 줄이 다음 단계다. 스크립트는 아래 순서에서 처음으로 빠진 것을 고른다.

| 순서 | 빠진 것 | 스킬 | 저장소에 남는 것 |
| --- | --- | --- | --- |
| 1 | 소스 코드가 없음(새 저장소) | `/repo-bootstrap` | 기본 스택의 타입·린트·경계 규칙·테스트·CI, check 명령 하나 |
| 2 | `AGENTS.md`의 `Rules and enforcement` 표 | `/repo-init` | 지금 무엇이 강제되고 무엇이 부채인지 적은 표 |
| 3 | check 명령 하나나 CI | `/repo-bootstrap`의 "기존 저장소" 절 | 기존 명령을 묶은 check 명령, CI, 기존 위반을 고정한 기준선 |
| 4 | `verify-*` 검증 스킬 | `/verify-init` | 앱을 실행해 증거를 남기는 절차와 기능 지도. `full-send`가 머지할 수 있게 된다 |
| 5 | 표에 `unenforced` 행이 있음 | `correct` | 가장 잦은 부채 하나를 구조·타입·린트·테스트로 옮긴 결과 |

이미 코드가 있는 저장소는 1을 건너뛰고 2부터 시작한다. 문서만 있는 저장소라면 1을 건너뛰고 2만 하면 된다. `next`가 `none`이면 기반은 갖춰진 것이다. 이후로는 3절의 사건이 생길 때마다 해당 스킬을 쓴다.

## 3. 사건별 스킬

파일의 상태로는 알 수 없고, 일이 생겼을 때 쓰는 스킬들이다.

| 사건 | 스킬 |
| --- | --- |
| 모듈을 더하거나 인터페이스·상태 소유자·의존 방향을 바꾸려 한다 | `codebase-design` |
| 같은 실수를 두 번 교정했다, 같은 리뷰 지적이 되풀이된다 | `correct` |
| 원인을 모르는 버그가 있다 | `diagnosing-bugs`로 고친 뒤 `correct`로 재발을 막는다 |
| 상태 기계·동시성·재시도·파서를 바꾼다 | `/formal-verify` |
| 앱의 기능·진입 경로·실행 명령이 바뀌었다 | `/verify-init`의 "지도를 맞춘다" 절 |
| 용어나 되돌리기 어려운 결정이 정해졌다 | `domain-modeling` |
| MR·PR을 올린다 | `file-mr`(증거 절) |
| 사람이 지켜보지 않는 동안 끝내야 한다 | `/full-send`(머지까지) 또는 `/full-stop`(머지 직전까지) |

## 4. 넘긴다

다음 단계의 스킬 이름과, 사람이 입력할 명령(`/repo-init` 등)을 알려 준다. 앞에 `/`가 붙은 스킬은 사람이 호출하는 스킬이라 스킬 도구로는 부를 수 없다.

사람이 이 대화에서 그 단계를 진행하라고 하면, 그 스킬의 `SKILL.md`(이 스킬 디렉터리의 형제 디렉터리)를 읽고 절차를 따른다. 사람이 없는 실행이면 다음 단계를 보고만 한다.

## 보고

칸별 상태, `next`와 그 이유, 사람이 입력할 명령, 지금 해당하는 사건이 있으면 그 스킬을 적는다.
