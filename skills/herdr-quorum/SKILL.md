# Herdr 쿼럼

결정 하나를 세 목소리(voice)가 근거로 다투고, 이 세션이 근거의 무게로 판정한다. 표 수가 아니라 확인된 근거가 결정한다. 산출물은 결정 기록 한 파일이다.

합의는 근거가 아니다. 첫 회차는 서로의 입장을 보기 전에 독립으로 작성하고, 판정자가 출처와 재현 결과를 확인한다. 미해결 반례나 인용 오류가 있을 때만 반박 회차를 연다. 확인된 근거로 결론을 낼 수 있으면 형식적인 추가 회차 없이 종료한다.

관점의 독립성을 높이기 위해 서로 다른 모델 계열을 선택한다. 계열 수 자체는 근거가 아니며, `omp models`와 `herdr integration status`에서 실제 후보를 확인한다. 두 계열만 사용할 수 있으면 그 사실을 기록하고, 되돌릴 수 없는 결정의 승인 경계는 그대로 지킨다.

시작 전에 `test "${HERDR_ENV:-}" = 1`을 확인한다. 실행 레시피와 agy 주의 사항은 `herdr-orchestrate` 스킬의 `references/launch.md`와 같다. 그 스킬이 없으면 `herdr agent`로 문법을 확인하고 프롬프트는 파일 경로 한 줄로 보낸다.

## 쿼럼을 열 때와 열지 않을 때

연다: 두 개 이상의 실행 가능한 선택지가 있고, 선택의 결과가 저장소 밖 근거(문서, 표준, 다른 프로젝트의 관행)로 갈리며, 되돌리기 비용이 있는 결정. 예: 라이브러리 선택, 저장소 관례 변경, 리뷰어의 `blocking`을 워커가 근거로 반박할 때.

열지 않는다: 저장소나 명령 하나로 답이 나오는 것(직접 확인한다), 이름·서식 같은 선호, 사람만 아는 값이나 되돌릴 수 없는 행동(`herdr-hitl`), 선택지가 하나인 것.

## 절차

### 1. 질문 파일

`<state>/quorum/<topic>/question.md`를 쓴다. `<state>`는 오케스트레이션 중이면 그 실행 디렉터리, 아니면 `${XDG_STATE_HOME:-$HOME/.local/state}/herdr-quorum/`이다.

```markdown
# <topic>

## 결정할 것
한 문장 질문.

## 선택지
1. ...
2. ...
(2~4개. 각 선택지는 지금 구현 가능해야 한다.)

## 제약
저장소가 이미 정한 것, 바꿀 수 없는 것, 성능·호환 조건.

## 근거로 인정하는 것
- 공식 문서, 표준 문서, 언어·프레임워크 문서의 정확한 URL
- 잘 알려진 오픈소스 프로젝트의 실제 코드 위치(URL)
- 이 저장소에서 실행한 명령과 출력
- 논문은 abs 페이지 URL
근거로 인정하지 않는 것: 도메인만 적힌 URL, "일반적으로 알려져 있다", 다른 목소리의 주장.

## 산출물
<state>/quorum/<topic>/position-<voice>-r<n>.md 에 아래 양식으로 쓴다. 마지막 줄 POSITION_DONE.

# 입장
선택지 번호와 한 문장 이유.
# 주장
- 주장 1 — 근거 URL 또는 명령과 출력
- ...
# 내 입장의 약점
가장 약한 곳 하나와 그것이 틀렸다면 무엇이 달라지는가.
# 반박 (2회차부터)
다른 목소리의 주장 가운데 틀렸다고 보는 것과 그 근거.
# 바뀐 점 (2회차부터)
입장을 바꿨으면 어떤 근거가 바꿨는지. 다수라서 바꾸는 것은 인정하지 않는다.
```

### 2. 목소리 배치

현재 워크스페이스에 `quorum:<topic>` 탭을 만들고 페인 셋을 나눈다(오른쪽 분할 뒤 오른쪽을 아래로). 페인 라벨은 `voice:<계열>`, 에이전트 이름은 `<run 또는 topic>-voice-<계열>`(예 `authref-voice-gpt`). 오케스트레이션 중이면 실행 슬러그를 붙여 살아 있는 이름과 겹치지 않게 한다.

```sh
herdr agent start <name> --kind omp --pane <p1> -- --approval-mode yolo
herdr agent start <name> --kind omp --pane <p2> -- --approval-mode yolo --model <다른 제공자 모델>
herdr agent start <name> --kind agy --pane <p3> -- --add-dir <state>
```

실행기가 아니라 실제 모델 계열을 나눈다. `omp-profile list`가 있으면 용도별 후보를 조회하고 OMP는 `omp-profile selector <용도>`의 전체 셀렉터를 `--model`로 넘긴다. AGY는 `agy models`의 ID를 명시한다. AGY의 Claude fallback과 OMP의 Claude를 서로 독립된 계열로 세지 않는다. Gemini를 선택한 AGY가 세 번째 계열이다.

목소리는 저장소를 읽고 명령을 실행할 수 있어야 근거를 만든다. cwd는 결정이 적용될 체크아웃(오케스트레이션 중이면 통합 워크트리)이다.

### 3. 1회차: 독립

세 목소리에 같은 한 줄 프롬프트를 보낸다: `Read <state>/quorum/<topic>/question.md and write your round-1 position as instructed.` 이 회차에서는 서로의 파일을 읽지 못하게 파일 이름을 알려 주지 않는다. 먼저 나온 입장에 나머지가 끌리는 것을 막기 위해서다.

세 파일에 `POSITION_DONE`이 다 생기면 근거를 확인한다. agy는 `--wait`의 `done`이 아니라 파일로 완료를 본다. 미해결 반례·인용 오류가 없으면 판정 단계로 간다.

### 4. 필요한 경우에만 반박

해결해야 할 구체적 쟁점과 다른 두 입장의 경로를 보낸다. `Read the positions at <paths>, check <unresolved claim> against its source or reproduction, and write your round-2 position.` 이미 확인한 내용을 반복하지 않고 새 근거를 확보한다.

3회차는 2회차에서 새로 확인된 근거가 입장을 바꿨을 때만 연다. 최대 3회차.

### 5. 판정

이 세션이 판정한다. 순서를 지킨다.

1. 세 입장의 근거를 표로 모은다(주장 | 근거 | 확인 결과). 근거 URL은 직접 열고, 명령은 직접 실행해서 확인/미확인/반증을 적는다. 미확인 근거는 무게가 0이다.
2. 확인된 근거의 무게로 선택지를 고른다. 세 목소리가 만장일치여도 근거가 미확인이면 결정하지 않는다. 한 목소리만 남았어도 근거가 확인되고 반증되지 않았으면 그쪽이다.
3. 남은 반대 의견과, 어떤 근거가 나오면 결정이 뒤집히는지(반증 조건)를 적는다.
4. 결정하지 못하면 이유를 셋 중 하나로 적는다: 근거 부족(프로토타입이나 측정으로 근거를 만들 수 있으면 `prototype` 스킬 등으로 그 일을 먼저 한다), 선호의 문제(사람에게 넘긴다), 되돌릴 수 없는 결정(사람에게 넘긴다). 사람에게 넘길 때는 이 기록을 첨부한다. 쿼럼 자체는 사람에게 묻지 않는다.

### 6. 결정 기록

`<state>/quorum/<topic>/decision.md`:

```markdown
# <topic>
결정: 선택지 N — 한 문장.
결정자: quorum (회차 수, 목소리 계열)
## 근거 표
| 주장 | 근거 | 확인 |
## 반대 의견
## 반증 조건
## 되돌리는 방법
## 목소리별 최종 입장
```

오케스트레이션 중이면 `decisions.md`에 같은 내용을 덧붙이고, 결정이 브리프의 계약을 바꾸면 영향받는 슬라이스의 브리프를 고친 뒤 워커에게 알린다.

### 7. 정리

목소리 에이전트는 종료하고 `quorum:<topic>` 탭을 닫는다. 기록 파일은 남긴다.

## 주의

- 판정자는 입장을 읽기 전에 근거 표를 먼저 만든다. 잘 쓴 문장과 긴 답변에 끌리는 편향을 줄이기 위해서다.
- 목소리에게 판정자의 선호나 워커의 사정을 알리지 않는다. 질문 파일이 목소리가 아는 전부다.
- 저장소 관례 변경이 결정되면 결정 기록에 "기존 관례가 통상 방식과 다른 이유를 저장소가 문서화했는가"를 확인한 줄을 남긴다. 문서화된 이유가 있으면 그 이유가 반증되지 않는 한 관례를 유지한다.
