# 리뷰 기준과 리뷰어 브리프

리뷰는 변경이 수용 기준을 만족하는지와 구체적인 위험이 남았는지를 확인한다. 독립 리뷰가 필요하면 새 컨텍스트에서 diff를 보고 시작하고, 가능하면 워커와 다른 모델 계열을 선택한다. 모델 다양성은 정확성을 보장하지 않으므로 판정에는 확인 가능한 근거가 필요하다.

## 리뷰어에게 주는 것과 주지 않는 것

준다: 오케스트레이터가 미리 저장한 diff와 커밋 목록, 브리프의 목표·계약·수용 기준·비목표, 저장소 관례 문서 경로, 아래 기준 전체. 리뷰어에게 셸로 diff를 생성하게 하지 않는다.

주지 않는다(1차 판정이 끝날 때까지): 워커의 `report.md`, 오케스트레이터의 판단, 이전 회차 리뷰. 판정을 다 쓴 뒤에만 `report.md`를 읽고 "검증" 절의 주장이 diff와 맞는지 대조한다.

## 실행 권한

리뷰어의 읽기 전용 경계는 역할 이름이나 프롬프트가 아니라 실행기의 실제 도구 집합으로 제한한다. [실행 레시피](launch.md)의 제한 reviewer 경로를 사용하고, 시작 시 유효 도구가 파일 읽기·검색만 포함하는지 확인한다. 셸, 쓰기, HITL, 다른 agent 호출, 확장·MCP 도구를 제공하지 않는다. 검증 명령이 필요하면 명령과 근거를 결과에 적고 오케스트레이터가 실행한다.

리뷰 결과는 stdout으로 반환하며 오케스트레이터가 산출물 파일로 저장한다. SDK가 생성하는 세션·압축 산출물과 모델이 호출할 수 있는 쓰기 도구는 다른 경계다. 압축 뒤에도 파일·산출물 읽기는 허용하되 은퇴한 custom compaction runtime/state에 의존하지 않는다.

## 판정 기준

각 항목은 통과/지적 중 하나로 답한다. 지적에는 `file:line`과 근거를 붙인다.

### A. 수용 기준

1. 브리프의 수용 기준 각 항목이 diff로 충족되는가. 충족 여부는 코드에서 읽어 판단하고, 실행 증거가 부족하면 필요한 명령과 기대 관측을 오케스트레이터에게 제시한다.
2. 계약 문장이 그대로 구현되었는가(이름, 시그니처, 스키마).
3. 브리프에 없는 변경이 있는가. 있으면 범위 이탈로 지적한다. 비목표에 적힌 것이 들어 있으면 blocking이다.

### B. 통상성

새 인프라·외부 연동·낯선 아키텍처를 도입할 때 기존 코드와 적합한 표준 라이브러리·서비스를 먼저 비교한다. 통상적인 국소 변경마다 외부 자료를 다시 조사하지 않는다. 대안이 더 낫다는 주장은 실제 비용·복잡도·위험의 근거로 설명하며, 관례와 다르다는 사실만으로 결함으로 판정하지 않는다.

이 저장소의 기존 코드가 통상적인 방식과 다를 때, 그 관례를 그대로 따른 변경은 지적 대상이 아니라 별도 표기 대상이다. `local-convention` 표지를 붙여 "저장소 관례 자체가 비표준이며 통상 방식은 X"라고 적는다. 고치라는 지시가 아니라 결정 후보다.

### C. AI slop 표지

다음은 살펴볼 단서이지 자동 결함 판정표가 아니다. 이번 변경에서 실제로 불필요하거나 위험하다는 근거가 있을 때만 지적한다.

- 호출자가 하나인 래퍼, 한 줄을 감싼 헬퍼, 나중을 위한 추상화나 매개변수
- 불가능한 상태를 막는 방어 코드, 광범위한 예외 잡기, 요청 없는 폴백과 기본값
- 코드가 이미 말하는 것을 반복하는 주석과 docstring, 변경 이력을 서술하는 주석
- 삭제 대신 남긴 별칭, 호환 shim, `deprecated` 경로, 이름만 바꾸고 옛 이름을 유지한 것
- 구현을 그대로 베낀 테스트, 모의 객체가 실제 동작을 대체한 테스트, 경계와 실패 경로가 없는 테스트
- 요청 없는 설정 항목, 기능 플래그, 텔레메트리, 재시도
- 문서와 메시지의 마케팅 어조, 이모지, "robust", "seamless" 류 형용사
- 같은 파일 안에 이미 있는 관례 옆에 세운 두 번째 관례

### D. 정확성

논리 오류, 경합, 자원 누수, 잘못된 경계 조건, 오류 처리 누락. 지적에는 재현 시나리오나 반례를 붙인다.

## 심각도

- `blocking`: 수용 기준 미충족, 계약 위반, 비목표 구현, 정확성·보안 결함처럼 통합을 막을 구체적인 문제. 재현이나 명확한 반례로 설명한다.
- `should`: slop 표지, 통상성 이탈 중 국소적인 것.
- `nit`: 이름, 서식. 도구가 강제하는 것은 적지 않는다.
- `local-convention`: 저장소 관례 자체에 대한 표기. 워커에게 보내지 않고 결정으로 올린다.

## 리뷰어 브리프 `slices/<slice>/review-brief.md`

```markdown
# <run>/<slice> 리뷰 <n>회차

당신은 이 변경을 처음 보는 리뷰어다. 작성자의 설명은 없다. 이 파일이 절차의 전부다. 다른 리뷰 스킬을 부르거나 서브에이전트를 띄우지 않고, 아래 기준을 직접 diff에 적용한다.

## 입력
- 워크트리: <절대경로>
- diff 파일: <오케스트레이터가 저장한 절대경로>, 커밋 목록: <절대경로>
- 브리프의 목표·계약·수용 기준·비목표: (그대로 붙임)
- 저장소 관례 문서: <경로들>. diff가 건드리는 영역에 해당하는 절만 읽는다. 두 줄 diff에 문서 전체를 읽을 이유는 없다.

## 기준
(위 A~D와 심각도 정의를 그대로 붙임)

## 산출물
다음 양식을 stdout으로 반환한다. 오케스트레이터가 `<state>/slices/<slice>/review-<n>.md`에 저장한다.

# 판정
blocking N건, should N건, nit N건, local-convention N건

# 항목
- [blocking] file:line — 무엇이 문제인가. 근거. 통상 방식과 참고 URL(해당 시).
- ...

# report.md 대조
(위 항목을 다 쓴 뒤 report.md를 읽고) 워커가 검증했다고 적은 명령 가운데 diff와 맞지 않는 주장.

마지막 줄에 REVIEW_DONE 을 단독으로 쓴다.
```

리뷰어의 프롬프트는 한 줄이다: `Read <state>/slices/<slice>/review-brief.md and carry it out exactly.`
